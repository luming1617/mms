## 一、背景与取舍

**1. 之前的架构，为什么去掉中间件？**
- 原来是 Mem0 + PG：`infer=false` 时 Mem0 只剩 embedding + 向量 CRUD，底层仍是 pgvector，与 PG 功能重叠。
- 两套系统意味着两套配置、鉴权、升级、备份和删除面，Mem0 的 history 还保留原文，端到端删除无法成立。
- Mem0 的关键词/实体信号以英文为中心，对多语言客服价值有限。
- 改后：一个库、一个事务边界、一条删除路径。代价是自己实现 embedding 流水线、分区、混合检索、对账。

**2. "删除只有一条路"怎么落地并验证？**
- 删除屏障：客户级 `customer_deletion_barrier`，写路径在同一事务内先取 advisory lock，再读主库 barrier，不读缓存。这样首次删除（屏障行还不存在）也没有窗口。每个 Job/候选/Outbox 带 `barrier_generation`，旧代际一律拒绝。
- 同事务内：记忆置 `DELETE_PENDING`，所有语言视图的向量置 `DELETED` 且 `embedding=NULL`，取消待处理 Job。检索读 barrier 缓存（TTL 5s），所以检索立即不可见。
- 后台清理证据、决策（脱敏保留最小审计）、Outbox、Kafka tombstone、日志、缓存、死信。
- 验证：先写外部 WORM 墓碑账本，再写 `deletion_tombstone`，对账通过才标 `COMPLETED`。账本失败则停在 `VERIFYING` 并告警。
- 备份：PITR 恢复后从外部账本重放墓碑，再开放流量。
- 门禁：删除与写入并发 100 轮，复活数为 0。

**3. 为什么不统一翻译成一种语言？**
- 翻译会改金额、日期、专名、版本号和错误码。
- 不同模型译文不同，事实身份不稳定。
- 原文才是可审计的证据。
- 所以事实身份靠"规范值"，翻译只用于检索视图，且译文不进入决策。
- 【需自补】有没有做过翻译方案的对比实验？

## 二、跨语言判重

**4. 规范层怎么产生？**
- Extractor 只输出原文语言和结构化 `object_json`（LLM 抽取，经 registry 的 schema/validator 校验）。
- Normalizer 按 `fact_key` 字典把数字、日期、枚举等归一成稳定 code，再用模板生成 `semantic_text`，由代码算 `semantic_hash`。
- 注意 `semantic_text` 是规范句，不是译文。
- 无法结构化的自由文本不自动写入，转 `NEEDS_VERIFICATION`。这是明确的代价。

**5. 怎么判重？**
- 先精确定位：`customer + fact_key + entity + value_slot`。
- 再比 `object_hash`（相同即同一事实）。
- 向量相似度只做候选发现，不能直接合并或覆盖，命中后进审核/冲突。
- 重复分两种：同值有新证据走 REINFORCE，新语言原文则追加该语言的原文视图。

**6. 92% 怎么测的？**
- 方案里的门禁是：中/英/西三语重述集（≥300 事实），同事实 `semantic_hash` 一致率要求 100%。
- 错误代价：误合并会丢信息，漏判只是冗余，所以误合并更严重。设计上宁可漏判（精确匹配加人工兜底），也不靠向量相似度去合并。
- 【需自补】92% 的评测集规模、构造方式、标注人，以及剩下 8% 的错误分布。

**7. 假矛盾与真矛盾？**
- 假矛盾：不同语言表述同一事实，或不同时间区间的不同值。判据是有效期是否重叠，重叠才可能冲突。
- 真矛盾（上海→深圳）：用户明确纠正且字段允许覆盖则 SUPERSEDE，旧版本保留在版本链里。
- 同级来源互相矛盾，或需要权威来源的事实，则进 `CONFLICT`，冲突期间不把任何一方当事实给 Agent。
- 时间建模：`valid_from/valid_to`、`cardinality`（单值/多值/时态）、版本链。

**8. 重复记忆还剩 10%，怎么降？**
- 方案没写原因分析，【需自补】。
- 可讲的思路：先按 fact_key 分桶看是哪类漏的；多半是自由文本和未覆盖 registry 的事实（被转人工）。解法是扩 registry、补 validator，再用语义候选做离线合并建议，而不是自动合并。

## 三、规则与安全

**9. 哪些不该记？**
- 硬规则先于评分，命中即终态。
- 拒绝：凭证/卡号、注入指令、不可信来源（助手生成/RAG 片段）、无证据定位。
- 高风险敏感信息默认拒绝，中高敏感还要单独授权。
- 退款、封禁等高影响事实必须有权威系统证据。
- 另有授权检查，撤回授权与删除共用同一屏障。

**10. "记忆只作参考，不当指令"怎么防？**
- 写入侧：注入模式命中则拒绝；只存纯文本；来源由服务端标注。
- 读取侧：返回结构里 `trust="untrusted_data"`，附服务端常量 `instruction_boundary`，调用方不能覆盖。
- Agent 的工具权限、审批、资金变更只来自可信控制层，不来自记忆。
- 红队集覆盖中英混合注入。

**11. "可验证"是什么意思？**
- 每条门禁有四要素：执行角色、环境、量化判据、证据归档。
- 删除：恢复演练后各表命中为 0，且有外部墓碑账本。
- 同意撤回：5s 内检索为 0。
- 触发器负向用例：故意写坏数据，要求被 DB 拒绝。

## 四、检索与性能

**12. 多副本并行检索，去重在哪做？**
- 每条记忆有 ORIGINAL（按证据语言）、CANONICAL（一条）、TRANSLATED（按目标语言）三类视图，最多 6 个。
- 向量检索一次覆盖所有视图，SQL 里按 `memory_id` 取最佳视图，所以去重在召回阶段，之后才进融合排序。
- RRF 融合时每个 `memory_id` 只算一票，再对 top 20 可选 rerank。
- 词法检索只对同语言、已配置语言启用，跨语言只承诺语义。
- 返回原文，同时带 `matched_view_kind` 等诊断信息。

**13. 新语言接入与存量回填？**
- 新语言只需加目标语言，异步 Translation Worker 生成译文视图，失败只降级该语言，不影响事实生效。
- 回填和重建优先级最低（500），不饿死新写入和删除。
- 成本控制：视图上限 6、翻译语言上限 4；高敏感记忆默认不翻译；超出需成本评审。

**14. 延迟预算？**
- 默认档 P95 ≤300ms，求和为 20 + 50 + max(96, 50) + 30 = 196ms（鉴权 + query embedding + 语义/词法并行 + 回表）。
- rerank 和权威回源只在扩展档（≤500ms）。
- 写入全异步：决策事务写记忆、Job、Outbox，embedding 由 Worker 做，失败走重试 → DLQ → 对账。
- 热路径不做提取和写入。

## 五、Agent 视角

**15. 怎么接入 Agent？**
- 方案里是 `/agent/memory-context` 接口，由服务端检索后返回上下文，是注入式。
- 我的取舍：自动注入延迟可控、实现简单；但可能注入无关记忆。
- 【需自补】你们实际是自动注入还是 tool 化，以及为什么这样选。

**16. 注入太多怎么办？**
- 有检索排序：状态/过期硬过滤 → 类型/可信度 → RRF → 同事实去重 → token budget 截断 → 可选 rerank。
- 冲突时：权威系统优先；用户明确纠正优先于推断；未解决的冲突不作为事实提供，而是返回 `requires_confirmation`。

**17. 与 Mem0/Letta/Zep 的差异？**
- 方案只写了移除 Mem0 的理由（见第 1 题）。
- 核心差异：事实身份由规范值决定，不由文本相似度决定；删除、授权、审计是一等公民；决策可回放。
- 【需自补】对 Letta、Zep 的了解；如果重选，是否还自研。可以说合规和多语言要求让自研更合适，但小团队可先用开源。

**18. 分五步和回滚？**
- 方案实际是 Phase 0–6，简历写"五步"，面试前需统一口径：契约冻结 → 最小闭环 → 异步/多语言/混合检索 → 检索质量与规模 → 评测与观测 → 生产化与灰度。
- 过关条件示例：写屏障零窗口，100 轮并发，屏障提交后新 ACTIVE 为 0。
- 灰度：先影子读（与旧版对比，不返回）→ canary 客户 → 逐步放量。
- 回滚：检索走旧版本，写入暂停，Job 保留，新数据不删；模型、规则、索引版本可独立回滚，回滚后也要跑 canary。
- normalizer 升版只重算投影，不改版本和状态，也可回滚。已用新规则写入的数据不用删，因为事实身份不依赖版本号。
